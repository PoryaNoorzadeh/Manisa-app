# M3 — Capability-based device experience

## M3.1 candidate: 0.11.0+15

OnOff remains the control capability. A separate, optional read of Descriptor
cluster 0x001D / DeviceTypeList attribute 0 discovers the product types reported
by each endpoint. Plug-in units 0x010A and 0x010B get Persian socket labels.
Other OnOff endpoints use a truthful single/multiple-output presentation. Endpoint
count is not evidence of the number of physical switch gangs. No dimming or
metering is claimed for a socket merely because its device type supports it.

The optional reader interface leaves existing controller mocks compatible. Type
metadata is cached alongside names, keyed by endpoint, with a missing-map default
for old installations. Discovery runs after state restoration, has a timeout,
and failures retain the existing controls and cached metadata. Commissioning,
fabric removal and OnOff command targets are unchanged.

## Acceptance and limits

Automated tests cover channel decoding, malformed/native error responses, JSON
round trips, legacy migration, endpoint identity, Persian labels, optional read
failure and slow/disposed UI behavior. Execution evidence is recorded separately
in the canonical register, not assumed from test creation.

Native Android compilation checks SDK compatibility. Fake controllers do not
prove native TLV decoding, BLE/network behavior, or a physical relay transition.
Real socket, mixed-output device, large text layout and hardware regression
remain manual acceptance items. Preserve the previous build as a rollback option;
this candidate is not a public-production readiness claim.

## Replanned sequence

| Step | Scope | Software exit criterion | Deferred hardware evidence |
| --- | --- | --- | --- |
| M3.1 | Descriptor-based labels and existing one/multiple OnOff controls | Analyze, existing suite, new model/channel/widget tests, Android build | Real declared types; restart; control/removal/re-pair regression |
| M3.2 — next | Discover actual LevelControl capability; simple dimmer percentage only where supported | Clamping, Persian percentage, throttled commands, failure/unknown state, mocked reports | Physical dimmer and external level changes |
| M3.3 | Optional power/energy capability discovery and read-only values | Units/scales, unsupported versus zero, stale/offline handling | Meter accuracy and live hardware reports |
| M3 close | Keep names, rooms, favorites and independent outputs consistent across supported controls | Cross-feature regression and candidate build | Track unresolved physical gates without relabeling them passed |
| M4 | Essential read-only sensors, chosen by available hardware | Unknown/stale states and accessibility tests | Sensor changes |
| M5 | Small, explicit user-triggered scenes | Partial failure, retry and duplicate-command behavior | Multiple-device execution |
| M6 | Minimal automation only after scenes are reliable | Ownership, scheduling and restart semantics agreed before implementation | Long-running reliability |
| Later gates | Thread support if required; security, signing, backup and release hardening | Separate scoped plans before commitment | Real network and release acceptance |

Build numbering remains monotonic; every APK includes semantic version, build,
commit metadata and SHA-256. Do not equate software milestone completion with
hardware acceptance or commit to a date before dependencies are known.
