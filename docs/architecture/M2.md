# M2 — Product Model

**Status: M2.1 rooms implemented; M2.2 home organization next**

## Goal

Turn the proven Matter controller path into a simple household product model without exposing protocol details in the normal user experience.

## M2.1 — Rooms and device assignment

- [x] Keep room metadata separate from the stabilized Matter controller and device store
- [x] Persist an ordered room catalog locally
- [x] Assign each Matter node to one room or to the explicit unassigned section
- [x] Load legacy devices with no migration prompt and show them under «بدون اتاق»
- [x] Create, rename and delete rooms in the Persian UI
- [x] Move assigned devices to «بدون اتاق» atomically when a room is deleted
- [x] Clear stale assignments that reference a missing room
- [x] Restore room grouping after the app is reopened
- [x] Validate model migration and essential UI flows with automated Flutter tests

Room assignments use the stable Matter `nodeId` internally. Endpoint, cluster and Fabric details stay outside the product-facing UI.

## Data boundary

```text
DirectMatterDevice store
  nodeId, device name, endpoints, channel names

Room catalog store
  rooms, nodeId → roomId assignment
```

Keeping these records separate avoids a migration of the validated Matter device format. A missing room catalog is interpreted as an empty catalog, so every existing device remains available under «بدون اتاق».

## M2.2 — Next slice

- Add a persistent single-home profile with a user-editable home name
- Add deliberate room ordering without drag-and-drop complexity
- Preserve the current one-tap device controls inside each room
- Add automated migration, ordering and reopen tests

Multiple homes, sharing, remote access, advanced dashboards and automation rules are outside this slice.

## Acceptance boundary

Automated tests validate persistence contracts and UI state transitions. Physical Matter behavior remains governed by the M1 hardware test register and continues in parallel; it is not reimplemented in M2.
