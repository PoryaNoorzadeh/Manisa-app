# M6.1 — Local scene schedules and connection recovery

Version: 0.22.0+27. Scope: schedules owned by this phone/app and automatic recovery of unavailable Matter devices. This milestone does not claim cloud, hub, or closed-app background execution.

## Scheduling contract

- A schedule selects one persisted manual scene, local time, weekdays and enabled state.
- Definitions and the last handled slot are persisted locally. A due slot is claimed before any device command is sent, giving at-most-once execution across app restarts.
- While the app is active, schedules are checked at startup, on foreground resume and once per minute.
- A missed slot is executed only when the app returns within ten minutes. Older slots are marked handled and skipped; they are never replayed later.
- Commands are not retried automatically. Execution reuses the existing scene runner, capability validation, per-action deadline and real device readback. Partial or unknown confirmation remains visible rather than being reported as success.
- Only one scene run may own the runner at a time. Opening the schedule editor or another active scene run prevents overlapping automatic execution.

## Connection recovery

- A failed device read preserves the last confirmed state but disables control and marks the node unavailable.
- The app retries unavailable nodes automatically with bounded backoff: 2, 5, 10, 20 and then 30 seconds.
- Before the retry, the Android bridge shuts down stale subscriptions and clears only local discovery/read tracking for that node. It does not unpair or forget the Matter fabric.
- Successful readback restores controls and resets the backoff without requiring the user to close and reopen the app. Foreground resume also triggers recovery.
- Manual “try again” remains available. Recovery never turns a failed write into an automatic command replay.

## Acceptance boundary

Automated tests cover schedule serialization, due-window claiming, duplicate prevention, skipped late slots, persisted claims and no-restart reconnection. Final validation still requires CI plus hardware checks for recovery after a real transport/session failure and scheduled multi-output scene readback.
