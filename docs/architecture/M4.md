## Protocol and state

Use connectedhomeip **v1.5.1.0**, matching the integrated Android build:

| Capability | Cluster / attribute | Wire unit and valid values |
| --- | --- | --- |
| Temperature | 0x0402 / MeasuredValue 0 | signed int16, 0.01 Celsius, -27315..32767 or TLV null |
| Relative humidity | 0x0405 / MeasuredValue 0 | unsigned uint16, 0.01 percent, 0..10000 or TLV null |

Primary contracts: [temperature XML](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/temperature-measurement-cluster.xml),
[humidity XML](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/relative-humidity-measurement-cluster.xml).

The native bridge reads these attributes with wildcard endpoints, then subscribes
only to paths actually returned. A product name or device type never enables a
sensor control. Initial values come from the device. Supported-null is unknown;
zero is a real reading; an absent attribute stays hidden. The app stores capability
metadata, never a last reading as durable truth. Legacy metadata defaults to no
sensor capabilities. Sensor-only nodes do not show invented OnOff controls or an
output-count label. A successful pairing is retained even when optional OnOff
discovery fails.

Sensor reports use a dedicated event channel and keep the existing OnOff, level,
color and electrical subscriptions. Minimum/maximum requested intervals are 5/60
seconds. Each metric has its own receipt time; after 90 seconds without a reading
it is marked stale (UI rechecks every 15 seconds, so indication may take up to 105
seconds). Null also refreshes receipt time but remains unknown. Subscription errors
mark the affected sensor subscription stale; a later partial report restores only
reported metrics. Sleeping/ICD devices and negotiated intervals beyond this policy
need hardware validation before a broader battery-sensor claim.

Late reads cannot overwrite a newer report or clear a newer stream error. Native
reads have a 14-second deadline and reply once; Flutter has a 15-second bound.
Removal, Activity destruction and superseded subscriptions invalidate callbacks
and release subscriptions. Failure of the optional sensor read does not disable
an otherwise working switch. Failed reads retain the last observation with a stale
indicator and a visible retry action.

## Verification and hardware follow-up

Automated checks exercise boundaries, negative/zero/null values, Persian formatting,
legacy storage, sensor-only nodes, sparse reports, error/retry, late-read races,
removal, reopen, coexistence with switches and narrow-screen large text.
Native compilation checks SDK/API integration; it does not prove physical sensor
accuracy. Hardware follow-up is a real temperature/humidity change, comparison with
an appropriate reference, network loss/recovery, app restart and removal/re-pair.
Record execution evidence and outstanding hardware results in
`docs/testing/M1-test-register.md`; do not relabel pending hardware as passed.

## M4.2: occupancy and contact states, candidate 0.18.0+23

Continue from M4.1 acceptance commit `1aa642c`. Reuse the sensor observation,
freshness, retry and cleanup path; keep environmental values and OnOff, RGB,
dimming and electrical controls intact.

| Reading | Required evidence | Meaning |
| --- | --- | --- |
| Occupancy | Occupancy Sensing 0x0406 / Occupancy attribute 0 | Occupied bit 0; valid bitmap values 0 or 1 become false/true |
| Contact | Descriptor 0x001D / DeviceTypeList contains Contact Sensor 0x0015 on that endpoint, plus Boolean State 0x0045 / StateValue 0 | true = closed, false = open |

Sources pinned to the build SDK:
[Occupancy XML](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/occupancy-sensing-cluster.xml),
[Boolean State XML](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/boolean-state-cluster.xml),
[device types](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/matter-devices.xml),
[official contact example](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/examples/contact-sensor-app/telink/src/AppTask.cpp).
The example writes `IsContactClosed()` into StateValue. Boolean State on another
or unconfirmed device type is not exposed as a door/window. Missing or malformed
Descriptor cannot invent contact semantics. Live contact reports rely on the
confirmed paths of the current subscription, not a cached product label.

Both binary attributes are non-nullable. The native channel transmits booleans;
Dart validates them strictly and normalizes to 0/1 inside the existing volatile
observation model. No persisted state or default boolean is used at startup.
Before the initial reading, the UI says unknown; after a failure it keeps the last
state with a stale indicator. It never turns unknown into closed or unoccupied.
Occupancy is labeled presence, without claiming a people count or a raw motion
event. Reports describe current state, not an event history or alarm guarantee.

Binary paths request a 1-second minimum interval and 60-second maximum; purely
environmental subscriptions retain 5/60. Per-metric freshness remains 90 seconds
with a 15-second UI check. Battery/ICD timing and Thread onboarding are not newly
claimed by this step. These read-only states send no control command.

The Android bridge uses `ManisaSensorCodec` for range, boolean and device-type
policy. A Kotlin host regression runner exercises that same policy before the
integrated SDK build. Flutter tests cover exact node/endpoint routing, false versus
unknown, metadata migration, sparse reports mixed with temperature, stale recovery,
reopen, removal/late reads and large Persian text. Existing M4.1/M3 tests stay in
the suite. Onboarding now uses a generic editable default device name instead of
assuming every added device is a switch.

Next: M4 close, limited to available battery/power information and cross-capability
regression. Scene execution remains M5; automation remains M6. Hardware acceptance
for these newly added binary states is recorded separately in the test register.

## M4.3 — Power source snapshots (0.19.0+24)

- Read Power Source cluster 0x002F on all endpoints including zero. Preserve multiple sources independently; do not assign a root battery to a particular sensor or infer the active source from the feature bitmap.
- FeatureMap (0xFFFC), Status (0), optional battery percentage (12, half-percent 0..200, nullable), charge level (14), replacement-needed (15), charging state (26), wired-present (9).
- Present only attributes the device returns. Unknown enum values remain unknown. Zero battery is known empty, not unknown. No fabricated percentage or voltage-based estimates.
- Deliberately on-demand snapshots: initial display, foreground resume and a dedicated refresh action. Every result is labeled last-read; no claim of live reporting, no periodic wakeup/polling of battery sensors. Values are not persisted. Empty response hides the panel; failures offer retry and retain only labeled previous values.
- Native 14s and Dart 15s timeout, node removal/read-generation guards, multiple source endpoints and large Persian text covered by regression tests.
- Existing sensor, RGB, endpoint names, metering and commissioning gates remain enabled. No Thread/ICD support is implied.
- Contract source: https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/power-source-cluster.xml
- Validation: pending CI/APK. New battery/power and M4 sensor hardware acceptance remains pending; prior user-confirmed hardware results remain accepted.
