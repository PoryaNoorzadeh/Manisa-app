## Protocol and state

Use connectedhomeip **v1.5.1.0**, matching the integrated Android build:

| Capability | Cluster / attribute | Wire unit and valid values |
| --- | --- | --- |
| Temperature | 0x0402 / MeasuredValue 0 | signed int16, 0.01 Celsius, -27315..32767 or TLV null |
| Relative humidity | 0x0405 / MeasuredValue 0 | unsigned uint16, 0.01 percent, 0..10000 or TLV null |

Primary contracts: [temperature XML](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/temperature-measurement-cluster.xml),
[humidity XML](https://github.com/project-chip/connectedhomeip/blob/v1.5.1.0/src/app/zap-templates/zcl/data-model/chip/relative-humidity-measurement-cluster.xml).

The native bridge reads these attributes with wildcard endpoints, then subscribes
only to paths actually returned. A product name or device type never enables a
sensor control. Initial values come from the device. Supported-null is unknown;
zero is a real reading; an absent attribute stays hidden. The app stores capability
metadata, never a last reading as durable truth. Legacy metadata defaults to no
sensor capabilities. Sensor-only nodes do not show invented OnOff controls or an
output-count label. A successful pairing is retained even when optional OnOff
discovery fails.

Sensor reports use a dedicated event channel and keep the existing OnOff, level,
color and electrical subscriptions. Minimum/maximum requested intervals are 5/60
seconds. Each metric has its own receipt time; after 90 seconds without a reading
it is marked stale (UI rechecks every 15 seconds, so indication may take up to 105
seconds). Null also refreshes receipt time but remains unknown. Subscription errors
mark the affected sensor subscription stale; a later partial report restores only
reported metrics. Sleeping/ICD devices and negotiated intervals beyond this policy
need hardware validation before a broader battery-sensor claim.

Late reads cannot overwrite a newer report or clear a newer stream error. Native
reads have a 14-second deadline and reply once; Flutter has a 15-second bound.
Removal, Activity destruction and superseded subscriptions invalidate callbacks
and release subscriptions. Failure of the optional sensor read does not disable
an otherwise working switch. Failed reads retain the last observation with a stale
indicator and a visible retry action.

## Verification and hardware follow-up

Automated checks exercise boundaries, negative/zero/null values, Persian formatting,
legacy storage, sensor-only nodes, sparse reports, error/retry, late-read races,
removal, reopen, coexistence with switches and narrow-screen large text.
Native compilation checks SDK/API integration; it does not prove physical sensor
accuracy. Hardware follow-up is a real temperature/humidity change, comparison with
an appropriate reference, network loss/recovery, app restart and removal/re-pair.
Record execution evidence and outstanding hardware results in
`docs/testing/M1-test-register.md`; do not relabel pending hardware as passed.
